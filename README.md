# rrb — Renewal Risk Brief

**One-page, fully-cited renewal risk briefs for 300 synthetic SMB medical
practices — with CI-gated tenant isolation.**

The scenario: you are *VitalPoint Software*, a fictional vendor selling
practice-management software to 300 small medical practices — dental, family
medicine, pediatrics, physical therapy and more, spread across the US — and
renewal season is coming.

`rrb` turns raw account data — contracts, usage metrics, support tickets,
QBR (Quarterly Business Review) notes — into a one-page brief that tells a
customer success manager exactly why an account is at risk of not renewing,
with every claim traceable back to a specific document. It runs entirely
offline: the data is synthetic, generated by a seeded script, and scoring is
a transparent rubric rather than a hosted model. What it does, end to end:

1. **Generate the dataset** — `rrb make-data` seeds 300 synthetic SMB
   medical-practice accounts (dental, family medicine, pediatrics, and
   eight more specialties) from ~12 hand-authored archetypes, each with its
   own usage pattern, support history, and narrative arc.
2. **Ingest** — SQLite (`data/rrb.sqlite`) is the system of record for
   accounts, usage metrics, tickets, and narrative documents (contracts,
   ticket bodies, QBR notes).
3. **Scoped retrieval** — every document is chunked and indexed into a
   hybrid BM25 + TF-IDF index, but the index is *only* ever queried through
   a per-account scope (see below).
4. **Risk rubric + satisfaction layer** — a transparent, weighted scoring
   function combines usage trend, ticket volume, seat utilization, and a
   lexicon-based sentiment score into a risk level (low / medium / high)
   with a fully itemized point breakdown.
5. **Brief with citations + "what we don't know"** — `rrb brief <account>`
   renders a markdown brief where every risk driver and every sentiment
   quote is backed by a verbatim excerpt from a real document (title,
   date, doc id), and an explicit "What We Don't Know" section names any
   signal that has no supporting evidence rather than inventing one.
6. **Evals** — `python -m evals.run_evals` scores the whole pipeline
   against the planted ground truth and fails the build if any gate
   regresses.

## Why tenant isolation is the point

The dataset is 300 SMB medical practices — a domain where "the model
mentioned a fact from a different customer's file" is not a UX bug, it's a
compliance incident. So the retrieval layer is designed so that a
cross-tenant leak isn't a rare failure mode that needs *detecting* — it's a
mode that isn't reachable. `HybridIndex` exposes no unscoped search API at
all: the only way to retrieve anything is `index.for_account(id).retrieve(query)`,
and that call builds its BM25/TF-IDF structures from *only that account's
chunks*. Another tenant's text is never loaded into the scope's scoring
structures in the first place, which is a stronger guarantee than filtering
ranked results after the fact — there is no ranked result to filter, because
the other tenant's documents were never indexed alongside this one's.

To make that guarantee checkable rather than asserted, every account gets a
unique "canary" phrase planted in its contract document and nowhere else.
The eval harness queries every other account's scope with every account's
canary and counts leaks; the gate for that count is zero tolerance — not
"95% isolated," but exactly 0, every run, or CI fails. Everything else in
the eval suite (risk accuracy, citation faithfulness, recall, abstention
honesty) has a numeric threshold it needs to clear; isolation is the one
metric in this project that isn't allowed to have an off day.

## Quickstart (no API keys required)
```
uv venv --python 3.12 && uv pip install -e ".[dev]"
.venv/bin/rrb make-data
.venv/bin/rrb brief acct_0042
.venv/bin/rrb serve          # dashboard at http://127.0.0.1:8078
.venv/bin/python -m pytest tests/ -q
.venv/bin/python -m evals.run_evals
```

## Evals

`python -m evals.run_evals` runs six checks against the planted ground
truth in `data/golden/labels.yaml` and exits non-zero if any gate fails —
this is the same command CI runs after every `rrb make-data`.

| Eval | What it measures | Gate |
|---|---|---|
| Tenant isolation | Every account's canary phrase queried against every *other* account's scope | `== 0` leaks (zero tolerance) |
| Isolation positive control | Each canary *is* findable inside its own scope, so zero leaks can't pass vacuously | `== 0` failures (zero tolerance) |
| Risk accuracy | `build_brief()`'s computed risk level vs. the archetype's planted risk label | `>= 0.75` |
| Satisfaction accuracy | Computed sentiment label vs. the archetype's planted satisfaction label | `>= 0.75` |
| Citation faithfulness | Every cited excerpt in a brief appears verbatim in its source document | `== 1.0` |
| Retrieval recall@5 | Planted evidence document is retrieved in the top 5 hits for its driver's query | `>= 0.75` |
| Retrieval MRR | Mean reciprocal rank of that evidence document — accounts hold only 3–8 chunks, so recall@5 comes cheap and MRR is the metric that actually grades ranking | `>= 0.7` |
| Abstention honesty | Accounts with withheld QBR notes are correctly flagged under "What We Don't Know" | `>= 0.9` |

## Optional: Claude prose upgrade

Everything above runs fully offline — no API key, no network call, no
external dependency beyond what `pip install -e .` pulls in. If
`ANTHROPIC_API_KEY` is set (and the `llm` extra is installed via
`uv pip install -e ".[llm]"`), `rrb brief` sends the generated markdown to
Claude for a single readability pass under a strict, citation-preserving
contract: keep every citation (title, date) exactly as given, keep every
quote verbatim, keep every section heading, add no new facts or numbers.
If the key isn't set, `maybe_rewrite()` is a no-op and returns the original
markdown untouched — the citation contract and the eval gates hold either
way, since the evals run against the offline pipeline.
